## 1. Executive Summary & Problem Motivation

When an autonomous AI agent interacts with an operating system via tools (e.g. running shell commands or modifying files), it explores possible solutions. If an exploratory action deletes a critical file, executes an unintended command, or produces side-effects visible to users or other processes, the damage is immediately permanent and irreversible. 

Prompt-level guardrails and host-level tool validators can be circumvented via prompt injection or unexpected input. Therefore, the operating system kernel itself must provide an **Externalization Barrier**.

### Core Concept: Speculation & Externalization
* **Externalization** is the moment an effect becomes visible to any entity other than the process that produced it.
* An effect that has **not** yet been externalized can still be cleanly rolled back or aborted.
* The speculative process **must** be able to read its own speculative writes (read-your-own-writes consistency).
* Hence, simple write-queuing fails; the kernel must maintain a **shadow copy** of modified blocks.

## 2. Kernel Mechanisms & Architecture

```
+-------------------------------------------------------------+
|                      User Processes                         |
|   Speculative Process (p->spec = 7)       Outside Process   |
|         |                   |                 (p->spec = 0) |
+---------|-------------------|-----------------------|-------+
          |                   |                       |
       bread()             bwrite()                bread()
          |                   |                       |
          v                   v                       v
+--------------------+  +--------------------+  +--------------+
| Look up in shadow  |  | Allocate / update  |  | Read real    |
| cache (spec == 7)  |  | shadow slot in RAM |  | block cache  |
+--------------------+  +--------------------+  | (dev, blkno) |
     | Found                 |                  +--------------+
     |                       v                        |
     v                +--------------------+          |
Return private copy   | shadows[NSHADOW]   |          v
                      | (Private RAM copy) |    Real Disk Block
                      +--------------------+
```

### The Six Key Requirements

1. **System Calls & Process Isolation (`xbegin`, `xcommit`, `xabort`)**:
   - `int xbegin(void)`: Allocates a new speculation identifier (`spec > 0`) for the calling process.
   - Child processes created via `fork()` inherit `p->spec` from their parent, grouping the entire process tree under the same speculation.
   - `int xcommit(void)`: Atomically commits all changes made by the speculation into real disk storage and flushes buffered outputs.
   - `int xabort(void)`: Discards all shadow copies and buffered outputs, resetting the process back to non-speculative state (`p->spec = 0`).

2. **Shadow Blocks at the Buffer Cache Level (`kernel/bio.c`)**:
   - Recommended design: shadow at the buffer cache layer (block level) rather than inode level.
   - Since inodes, directory entries, and data bitmaps are all stored in disk blocks, shadowing blocks automatically handles creates, writes, truncations, and unlinks without modifying higher filesystem logic!
   - Data structure in `kernel/bio.c` / `kernel/param.h`:
     ```c
     #define NSHADOW 64 // 64 KB of kernel memory (64 * BSIZE)
     struct shadow {
       int spec;          // Owning speculation ID (0 = free)
       uint blockno;      // Disk block number being shadowed
       char data[BSIZE];  // Private buffer contents
     };
     ```
   - On `bread(dev, blockno)`:
     - If `p && p->spec`: search `shadows[]` for `(p->spec, blockno)`. If found, return the shadow copy.
     - Else: fall back to the standard `bcache` path.
   - On `bwrite()`:
     - Speculative writes allocate/update a slot in `shadows[]`.
     - **Critical Rule:** If `shadows[]` is full, the write **MUST FAIL WITH -1**. It must *never* fall back to the real disk, because that would externalize uncommitted speculative state!

3. **Externalization Barriers: Console Output & Pipes**:
   - **Console Output (`kernel/console.c`)**:
     - Output generated by speculative processes must be stored in a memory ring buffer.
     - Output is only printed to the physical UART/console upon successful `xcommit()`.
     - On `xabort()`, the buffered console text is discarded.
   - **Pipes (`kernel/pipe.c`)**:
     - Rule: Buffer pipe writes **only if the reader is outside the current speculation**.
     - If the reader is inside the same speculation, allow immediate data transmission. (Buffering writes within the same speculation deadlocks pipelines such as `cat file | grep text`!).

4. **Directory Operations (Create & Unlink)**:
   - With buffer-cache level shadowing, creating a file or unlinking a file simply modifies inode blocks and directory data blocks.
   - Speculative `unlink` will make the file vanish for the speculative process, while outside processes continue to see the original block on disk until `xcommit`.

5. **Atomic Commit & Abort**:
   - On `xcommit()`:
     - In a single log transaction (`begin_op()` ... `end_op()`), write each dirty shadow block to the real buffer cache (`log_write()`).
     - Release console buffer **strictly after** `end_op()` returns, preventing false output if a crash occurs during disk log commit.
     - Note the log size constraint: `MAXOPBLOCKS` is 10, while `LOGBLOCKS` is 30. Either ensure batching within transaction limits or document atomicity boundaries.
   - On `xabort()`:
     - Zero out the shadow entries for `p->spec` and reset console buffers.

6. **Conflict Resolution Rule**:
   - Define policy for when a non-speculative process modifies a block that the speculative process has also modified.
   - Course-defensible policies:
     - *Policy A (Abort on Conflict):* If an outside write touches a shadowed block, abort the speculation.
     - *Policy B (Commit Wins):* Overwrite real block on commit.
     - *Policy C (Versioned Read-Set):* Maintain read timestamps; abort only if read before outside write.

## 4. Evaluation Criteria & Hidden Tests

1. **Write Cost Cliff**:
   - A benchmark testing file writes from 1 KB to 64 KB inside and outside speculation.
   - The graph must clearly display the "cliff" where `NSHADOW` (64 KB) runs out and returns `-1`.
2. **Hidden Test Defenses**:
   - Nested `xbegin()` calls (proper error handling / depth tracking).
   - Crash during `xcommit()` (journaling integrity via QEMU crash harness).
   - Shadow block exhaustion behavior (strict refusal vs leak).
   - Laundering / side-channel tests (e.g. attempting to leak speculative info via pipe to outside process).
3. **Viva Requirements**:
   - Live code modification on the spot.
   - 2-page strictly formatted handwritten report.
   - QEMU logs and GDB debug session trace.
